## Current source boundary

At this baseline Main registers only AuthRoutes, not VerificationRoutes or proof
routes. Verification core and encrypted delivery storage exist; the separately
opted-in delivery worker defaults false. Both contact receipts deliberately leave
an enrollment ineligible pending trusted projection. Positive projection/ACTIVE
authority and all-entry eligibility enforcement are unimplemented. Proof routes
have no handlers (404), not an implemented unavailable-port 503. Proposed flags
cannot expose them through current Main. The provider extension is disabled and
unregistered; source or synthetic tests do not prove runtime hooks or activation.
This is a source-baseline statement, not verification of a live deployment.

Existing KeycloakTokens validation remains unchanged: exact issuer, Bearer type,
armoney-api audience, clients armoney-ios/armoney-android/armoney-web, expiry and
applicable nbf. Present azp must match the issuing client; web requires azp.
Preserve public OIDC endpoints, callbacks, state/nonce and S256 PKCE. Historical
proof claims must never replace those checks or identify accounts by email.

## Authority and supported flow

Keycloak validates password, authorization code, redirect, client, session and
S256 PKCE. Auth owns durable proof records, current banking eligibility and
notification deduplication. Proof storage is not a substitute for those checks.
Only exact `response_type=code` with absent or `query` response mode is supported
when this extension is enabled. Reject hybrid, implicit, fragment, form-post and
other modes; do not classify an unsupported mode as cookie reuse. Preserve
issuer, subject, public client IDs, callbacks, state, nonce and PKCE behavior.

At successful redirect, derive proof only from the code just generated by the
provider and the current server authentication session. Require exactly one code
in the generated 302 Location. A real password authenticator creates one random
UUID event and password timestamp after successful credential validation, in the
current authentication session only. Failed passwords create neither. The marker
must never be copied into reusable user/client session notes. No marker means
`reuse`, not evidence of fresh password entry. Required actions and auth-owned
ACTIVE eligibility must already have passed before proof creation.

## Code digest, keys and limits

Both provider hooks compute exactly:

```text
code_digest = lowercase_hex(HMAC-SHA256(code_key,
    LP("armoney-login-code-v1", code_key_id, issuer, subject,
       client_id, user_session_id, canonical_code_data_id)))
LP = concatenate four-byte unsigned big-endian UTF-8 byte length, then bytes,
     for each field, in the stated order; no separators or null fields
```

`canonical_code_data_id` is the immutable UUID `OAuth2Code` data ID in lowercase
hyphenated UUID form. The redirect hook extracts it only from its generated code,
checking code structure and server-owned session/client context. The validated
code-grant hook uses `parseResult.getCodeData().getId()`. Never hash an incoming
browser parameter to create a proof. Never send the redeemable code, code-data
ID, password, access token or refresh token to these auth endpoints.

The code HMAC key is independently provisioned, exactly 32 random bytes encoded
as canonical base64. It is distinct from OTP HMAC, delivery encryption, provider
binding and all HTTP credentials. Provider instances share the same key ring.
Auth receives only the digest and an allowlisted key ID, and authenticates its
writer; it cannot recompute or certify the digest without the code-data ID.
Key IDs match `[A-Za-z0-9_-]{1,32}`. Permit current plus one previous key.

Maximum request/response is 12 KiB; strict JSON rejects duplicate, unknown and
wrongly typed fields. Subject and server session bindings are 1..255 characters
without whitespace/control characters; issuer is an exact configured HTTPS realm
URL, at most 512 characters. `client_id` is an exact configured allowlist entry,
matching `[A-Za-z0-9_-]{1,128}`. UUIDs use full hyphenated form. Times use RFC3339
UTC at integer-second precision. Auth uses database time for all validity checks.

Initial bounds: code validity at most 120 seconds, `issued_at` at most 30 seconds
behind/ahead of auth database time, `issued_at < expires_at`, and
`now < expires_at <= issued_at + 120 seconds`. `expires_at` equals the provider's
actual code expiry; auth never extends it. Interactive password time satisfies
`issued_at - 1800 seconds <= password_authenticated_at <= issued_at`.
The provider must reject incompatible configured lifetimes instead of truncating
an already valid code's lifetime or inventing a password timestamp.

Persist the selected key ID and write command with the current authentication
flow/code until acknowledgement; a retry must not choose a new key or event.
Rotation keeps the previous key available for at least 180 seconds after the last
old-key write and until all its unexpired codes finish. Resolve computes at most
two candidate digests from validated server code data. A missing current-key
record may try the previous key. A found mismatch, expiry, unavailable response
or ambiguous/multiple match fails closed; it is not a downgrade to `reuse`.

## Private HTTP agreement

Both endpoints are provider-to-auth only, excluded from gateway/public ingress.
Use fixed destinations, no redirects, two-second connect and four-second request
deadlines. Use independently provisioned printable 32..256-character credentials:

| Operation | Credential | Header |
| --- | --- | --- |
| Write | `SSO_LOGIN_PROOF_WRITE_KEY` | `X-ArMoney-Login-Proof-Write-Key` |
| Resolve | `SSO_LOGIN_PROOF_RESOLVE_KEY` | `X-ArMoney-Login-Proof-Resolve-Key` |

These keys differ from one another, `SSO_VERIFICATION_BRIDGE_KEY`, provider status
credentials, business service keys, code HMAC keys and OAuth client secrets.
A resolver credential cannot create proof. No bearer session or client identity
header authorizes either operation. All replies use `Cache-Control: no-store`.

### POST `/internal/sso-login-proofs`

Required fields, with explicit JSON nulls where stated:

```text
command_id: UUID
code_digest: exactly 64 lowercase hexadecimal characters
code_key_id: allowlisted key ID
issuer, subject, client_id, user_session_id, authentication_session_id: strings
issued_at, expires_at: timestamps
kind: "interactive" | "reuse"
event_id: UUID for interactive; null for reuse
password_authenticated_at: timestamp for interactive; null for reuse
```

Auth rechecks the trusted issuer/subject's current ACTIVE identity, both current
contact receipts, verification epoch, exact projection acknowledgement and
current provider-contact/session observations. Missing integration or uncertain
dependencies must reject; never fabricate an ACTIVE identity or infer eligibility
from provider booleans, `sid`, `auth_time`, email equality or mutable attributes.

One auth transaction reserves unique `(issuer, code_digest)`, compares the full
canonical payload and requester-scoped command hash, and writes its immutable
snapshot. Requester scope is the authenticated writer plus issuer/client, not an
untrusted identity header. Exact command/payload replay returns the original
acknowledgement, including after response loss. Changed payload for the same
command or code binding returns generic 409. A duplicate code with a different
command may return the original acknowledgement only after complete payload
comparison excluding command ID; it must never overwrite anything.

For interactive proof, unique `(issuer, event_id)` also binds subject, client,
user session, authentication-session binding and password time. Reusing that
event in another such tuple conflicts. Multiple codes from the same password
flow may reference the same event and immutable recipient/epoch snapshot; they
cannot generate extra notices. Reuse has no event row and is always ineligible.
Auth alone captures the authoritative verified email/version at event creation;
provider contact fields never choose a notification recipient.

Return 200, for first commit and exact replay:

```text
proof_id: UUID
code_key_id: string
state: "RECORDED"
event_id: UUID | null
kind: "interactive" | "reuse"
login_notice_eligible: literal boolean
issued_at, expires_at: the original immutable timestamps
```

`login_notice_eligible` is true only for an interactive event with the complete
auth-owned verified recipient and eligibility snapshot. It is historical notice
metadata, never a banking authorization. A missing storage acknowledgement
withholds the redirect. An uncertain commit is retried with the same command and
code; no rollback or successful redirect is inferred. Orphan committed proofs
are harmless without a valid provider code and expire normally.

### POST `/internal/sso-login-proofs/resolve`

Required fields: `code_digest`, `code_key_id`, `issuer`, `subject`, `client_id`,
`user_session_id`. Call only after Keycloak has validated the code, current user
and session, client, redirect, expiry and PKCE. The auth snapshot binds the stored
authentication session; that pre-token object is not reconstructed from client
input or required as an unavailable token-grant parameter.

Return 200 with exactly `proof_id`, `event_id`, `kind`,
`login_notice_eligible`, `issued_at`, `expires_at`. This is a read-only lookup:
no proof consumption, event creation, recipient changes or eligibility rewrites.
The exact tuple must match and database `now` must be strictly before expiry.
The resolver is not a second code redemption service. Keycloak's own single-use
code check rejects code replay even when this lookup can be repeated.

Both operations use 400 malformed, 401 invalid directional credential, 409
conflict/current eligibility rejection, 410 expired, 429 bounded capacity with
`Retry-After`, and 503 unavailable/uncertain. Resolve alone uses 404 for absent
proof, allowing only the bounded previous-key lookup. Bodies stay generic and
contain no contacts, binding, digest, codes or tokens. No error becomes an
eligible or invented `reuse` result.

## Three signed claims and auth-local notice port

Keep exactly the existing proposed three custom access-token claims:

- `armoney_login_event_id`: canonical UUID for interactive; absent for reuse.
- `armoney_login_kind`: literal `interactive` or `reuse`.
- `armoney_login_notice_eligible`: literal JSON boolean.

Only the validated authorization-code token-response hook copies this immutable
snapshot into the access token before signing. Interactive true requires a valid
event UUID; reuse requires no event and false. Missing/malformed/inconsistent
claims cannot create a notice. There is no fourth timestamp claim. Refresh,
password grants, token exchange and other grants must not copy these claims or
construct new eligible events. Explicitly test refresh-token copying.

Introspection preserves only those validated values from the original signed
access token. It never reconstructs them from mutable session notes, a later
password event or a fresh proof lookup. Token A's three claims stay unchanged
after login B. Current eligibility enforcement is a separate check that may deny
banking access; it never rewrites A's historical event identity.

Planned auth-local application port required before activation:

```text
LoginProofEvents.resolveForNotice(
    issuer, subject, client_id, user_session_id, event_id)
  -> {identity_id, event_id, password_authenticated_at,
      verified_email_snapshot, email_contact_version, verification_epoch}
```

Invoke only after authenticated introspection, strict three-claim validation and
current ACTIVE/epoch/contact enforcement. Resolve against auth's own durable
event row with the exact tuple, never another service's database. A missing or
mismatched event cannot capture an eligible notice. `occurred_at` comes from its
frozen password timestamp, never `auth_time`, access-token `iat`, session notes
or the time of bank exchange. Snapshot email must never be readdressed from a
later contact update. Legacy/unproven events are skipped, not approximated.

Session digest creation and notice capture remain one auth transaction. Derive
the outbox ID/deduplication key from the trusted `(issuer, event_id)` tuple, with
complete identity/recipient/time comparison on duplicates. Current broad
`ON CONFLICT DO NOTHING` must not silently accept conflicting event payloads.
Repeated bank exchanges of the same original token may create banking sessions
when current eligibility permits, but at most one notice event. SMTP remains
outside authentication: provider failure cannot revoke a successful session.

## Retention, concurrency and activation gates

Retain proof, command replay and event metadata for seven days; notification
recipient snapshots are erased after 24 hours. Unexpired access tokens must have
at most a 900-second lifetime before activation, so recipient expiry cannot
readdress a still-valid first exchange. Keep minimal outbox event tombstones
through every accepted token/replay lifetime. Exact expired writes/lookups reject
and never reopen proof. After the seven-day idempotency horizon, original
requests still fail timestamp bounds; comparison of deliberately reused command
UUIDs with new payloads is not promised beyond that documented horizon.

Cleanup uses database-time bounded batches, e.g. 100 rows per transaction, without
removing a referenced in-flight recipient or an unexpired event. Set initial hard
caps of 100000 retained proofs and 100000 commands, plus a global maximum of 1000
new proofs/hour; existing exact replay remains readable at capacity. A configured
trusted-proxy-source budget is an activation gate; arbitrary forwarded headers
never create unbounded source maps. Capacity fails closed and needs operational
visibility. No code, token, full contact or body goes to logs/events.

Acceptance must cover two provider instances and auth restart, concurrent exact
writes, conflicting writes, two-tab different-code isolation, immutable old-token
introspection after a later password login, response-loss retry, exact expiry,
key overlap, code replay, refresh/other grants, unsupported response modes,
current-eligibility outage/revocation, immutable email snapshots and SMTP outage.
Real PostgreSQL and isolated pinned-provider/browser tests plus independent
security retesting are required. Pure-JDK fixtures cannot prove these properties.

## Dependency closure and activation gates

The unpublished auth patch has proof domain/application/persistence/configuration
and route candidates. They are absent from this clean provider slice. A later
integration needs an exact lease, compatibility review and fresh tests. Do not
copy old Main, notice lifecycle, migration numbers or test results wholesale.
Current main owns V6 registration verification; allocate the next unused migration
against the actual clean lineage and preserve append-only publication semantics.

Required auth closure before positive proof:

- Immutable proof/event storage, requester-command hashes, concurrency constraints,
  database-time expiry, cleanup, retention and bounded capacity.
- Directional write/resolve transport, strict bounded JSON, allowlists, generic
  errors, no-store and lifecycle wiring. A deliberately unavailable eligibility
  port must return 503 for otherwise valid new writes after wiring; that is
  future behavior, not today's absent route.
- Trusted eligibility authority for issuer/subject, both current contact versions
  and receipts, verification epoch and exact user-projection acknowledgement.
  Provider observations do not certify verification or ACTIVE. Uncertain or
  outdated authority denies eligibility.
- Authenticated fixed private current-provider status/session/contact port and
  exact server-derived authentication-session binding. Browser form IDs, client
  contacts and mutable session notes are not evidence.
- All-entry banking/session enforcement, contact-change and revocation handling,
  and explicit legacy identity migration policy. Never relink/delete/verify an
  existing UUID by email matching.
- Original-token three-claim parsing, local event lookup above, frozen verified
  recipient and password time, transactional session/notice deduplication and
  independently retryable notice delivery. No sid/auth_time approximation. The
  old worktree's first-observation notices are absent from this baseline.

ARMONEY_LOGIN_PROOF_ENABLED names the disabled provider proof opt-in.
AUTH_LOGIN_PROOF_BRIDGE_ENABLED names the earlier auth transport candidate; it
is not read or wired by current Main. AUTH_SSO_LOGIN_PROOF_ENABLED remains a
proposed positive-enforcement gate, also unimplemented here. Final auth flag
names/ownership require freezing before wiring. No flag supplies missing
projection authority. OTP delivery opt-in cannot activate proof or login notices.

Keep provider factories unregistered and every proof/bridge/enforcement gate
disabled until complete dependency closure, operational bounds, legacy policy,
real PostgreSQL/pinned-provider/browser acceptance and independent security
retesting pass on the integrated revision.
