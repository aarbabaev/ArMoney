# ArMoney identity provider

Runtime: `quay.io/keycloak/keycloak:26.7.4`, pinned from the [official downloads](https://www.keycloak.org/downloads.html). This directory is configuration, not a Java module. Mount `armoney-realm.json` read-only in `/opt/keycloak/data/import/` and start with `start --import-realm`. Keycloak supports [environment placeholders](https://www.keycloak.org/server/importExport); supply `SSO_CLIENT_SECRET` to Keycloak and auth-service. No user accounts or secret values are committed.

Use a dedicated PostgreSQL database/volume. Set `KC_HTTP_RELATIVE_PATH=/sso`, `KC_HTTP_ENABLED=true`, `KC_HOSTNAME` to the exact external HTTPS base URL including `/sso` and `KC_PROXY_HEADERS=xforwarded` behind the trusted TLS edge. Do not publish the Keycloak application or management ports directly. The edge must overwrite forwarding headers and restrict administration endpoints. Startup import skips an existing realm: later configuration changes and secret rotation require deliberate administrative updates, not deleting its volume.

The separate `armoney-ios` and `armoney-android` public clients use authorization code with mandatory S256 PKCE. Each has exactly one callback and one post-logout URI:

| Client | Authorization callback | Post-logout callback |
| --- | --- | --- |
| `armoney-ios` | `com.armoney.ios:/oauth/callback` | `com.armoney.ios:/oauth/logout` |
| `armoney-android` | `com.armoney.android:/oauth/callback` | `com.armoney.android:/oauth/logout` |

Password grants, implicit grants, service accounts, device authorization and CIBA are disabled. The native client uses the system authentication browser, validates state, and exchanges the access token through auth-service; it does not use an ID token as authentication evidence. The server validates identity through authenticated introspection. Local session credentials are kept in Keychain on iOS and Keystore-encrypted app-private no-backup storage on Android. The private `armoney-auth` client authenticates server-side introspection and has no user grant flows or service account.

POST `/v1/auth/sso` accepts only `{ "access_token": "<provider access token>" }` (8192 characters maximum, 12288-byte body). Auth checks the provider's active result, expiry, issuer, API audience, issuing client from the exact `armoney-ios`/`armoney-android` allowlist and subject. If `azp` is present, it must match that issuing client; listing both clients does not permit cross-client mismatches. Provider failures return 503; unacceptable tokens return 401; malformed input returns 400. It creates/reuses a local UUID keyed by the exact issuer and subject. Email and phone are never automatic identity-linking keys; `/v1/auth/me` returns `email: null` for these principals. Legacy credential identities remain separate even if the same person uses both methods. New bank enrollment also requires a canonical phone from trusted introspection and an atomic unique phone binding in auth-service. A collision does not create a bank identity or session. The result of a successful exchange is a new independent 30-minute opaque ArMoney session; only its digest is stored.

POST `/v1/auth/logout` revokes only the supplied ArMoney session. The iOS client also opens the provider's OIDC end-session endpoint with client_id and the configured post-logout redirect, then clears local credentials. The provider may require confirmation because this flow supplies no ID-token hint. Android currently removes its local bank session and attempts bank-session revocation; its browser SSO cookie may remain active. Provider logout/revocation does not revoke an already issued ArMoney session; its expiry/local logout remains authoritative. The native clients do not request offline access or implement refresh. Each starts a fresh browser SSO flow when its ArMoney session expires.

The disposable CI smoke adds one exact loopback redirect to each native client in its isolated realm only. It registers the first synthetic identity through the hosted form and creates a second synthetic identity administratively. It rejects missing, malformed, non-UAE and duplicate phones through the real registration form, then drives browser authorization with S256, state and nonce, exchanges the returned code and calls the public exchange and protected profile APIs. The browser script checks phone introspection with only `scope=openid`, wrong verifiers, code replay, client/redirect binding, ID-token rejection, shared issuer/subject identity across native clients, local logout and separate-owner isolation. Adapter unit tests cover wrong audience/client/issuer, cross-client `azp`, malformed claims and provider failure. Native clients validate callback state independently. Never enable a password grant to replace this flow and never seed the persistent developer stack. Numbers `+971509990001` and `+971509990002` are reserved for this disposable script only; no SMS is sent.

References: [OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [client and PKCE configuration](https://www.keycloak.org/docs/latest/server_admin/index.html), [hostname configuration](https://www.keycloak.org/server/hostname).

Keycloak 26.7.4 requires the authenticated introspection client to appear in the token audience. Both native clients' access tokens therefore have both `armoney-api` and `armoney-auth` audiences. Auth-service still requires `armoney-api` and an issuing client from the exact native-client allowlist; no introspection audience-check compatibility bypass is enabled. Both audience mappers exclude ID tokens. See the [pinned provider implementation](https://github.com/keycloak/keycloak/blob/26.7.4/services/src/main/java/org/keycloak/protocol/oidc/AccessTokenIntrospectionProvider.java).


## Existing realm upgrade

Editing this export and restarting with `--import-realm` does **not** update an existing `armoney` realm. Its users, client secrets and issuer/subject mappings remain in the persistent database. Adding Android to an existing realm requires an explicitly authorized administrator to create the separate `armoney-android` client with the exact settings above and the two audience mappers from this export, then verify the persisted configuration. Preserve the existing iOS and confidential `armoney-auth` clients, users, issuer URL and database volume. Do not delete/re-import the realm or rotate unrelated secrets to add Android.

The source change and disposable browser tests do not establish that a developer's running realm has been upgraded. No live administration commands are executed by this change. Native-device callback dispatch and LAN certificate validation also require device evidence beyond the browser loopback tests.

## UAE phone registration and migration

New hosted registrations use the Keycloak username as the mandatory canonical UAE mobile number, displayed as **UAE mobile number (+971)**. The accepted pattern is `^\+9715[024568][0-9]{7}$`; the hosted form accepts the full `+971` form and has no country selector. Phone editing is disabled after registration. Keycloak's database enforces username uniqueness within the realm. The ordinary email and name fields remain unchanged. Email login remains available for compatibility; usernames and phone numbers are not substituted for the stable issuer/subject bank identity.

Both native clients directly map the built-in username property to `phone_number` in access tokens and introspection, so no optional `phone` scope is required. There is no second editable phone attribute. The mapper does not claim verification. No SMS or external verification provider is configured: the bank phone is a user-claimed address with `phone_verified=false`, which can receive phone-addressed P2P payments. Registration and the payment confirmation UI must not represent that address as proof of ownership.

ArMoney registration finishes at the successful bank token exchange. Auth-service enforces global phone uniqueness across new legacy registrations and SSO bank enrollment. If a legacy identity already holds the number, the Keycloak registration may exist while bank enrollment is rejected. It must never silently link those identities, overwrite a binding, or issue a bank session on a collision. Cross-store uniqueness at the Keycloak form itself would require a separate coordinated reservation protocol and is not implemented.

Existing legacy accounts, sessions, Keycloak subjects and bank UUIDs remain intact. Existing mapped SSO users with old non-phone usernames can continue logging in without acquiring a phone binding; an unmapped subject without a canonical phone cannot create a new bank identity. Keycloak 26.7.4's [profile validation](https://github.com/keycloak/keycloak/blob/26.7.4/server-spi-private/src/main/java/org/keycloak/userprofile/DefaultAttributes.java) tolerates an unchanged invalid value when the attribute is read-only. Keep `editUsernameAllowed=false`; do not relax the new-registration regex or rename existing usernames automatically. Migrating an existing user's phone requires an operator-reviewed process preserving subject and bank UUID, checking global uniqueness and resolving conflicts. Phone claiming does not establish phone ownership.

`phone-user-profile.json` is the readable profile configuration. The realm import contains the same JSON serialized under the `org.keycloak.userprofile.UserProfileProvider` component (`declarative-user-profile`, `kc.user.profile.config`). Keep both representations synchronized. This is Keycloak's component configuration, not an unsupported top-level `userProfile` realm property.

For an existing realm, an authorized administrator can run `apply-phone-registration.py` with a short-lived administrator token supplied through `KEYCLOAK_ADMIN_TOKEN`. Use a private trusted administrative endpoint and normal certificate verification; never publish the admin API. For example, in an administrator-controlled environment:

```text
python3 sso-service/apply-phone-registration.py --admin-base https://keycloak-admin.example/sso
python3 sso-service/apply-phone-registration.py --admin-base https://keycloak-admin.example/sso --apply
```

The first invocation reads configuration and describes the update without writing. Review a protected backup and the migration policy before the second invocation. The helper merges only username profile settings, disables email-as-username and username editing, and upserts the two native-client phone mappers. It preserves other profile fields and does not update users, credentials, issuer, secrets, redirects, grants or audience mappers. Both native clients must already exist. Administrative operations are not atomic across resources: on failure, investigate the partial update and rerun deliberately; do not delete or re-import the realm. Do not run the helper automatically on startup or from CI against a persistent environment.

After applying, read-back verification establishes only configuration persistence. Independently test hosted registration (including duplicate rejection), both native-client exchanges, existing non-phone user login, existing bank identity continuity and cross-entry-point phone collision handling. The helper has not been executed against the user's realm. Full repository checks and disposable Compose acceptance remain delivery requirements.

The offline helper regression uses synthetic in-memory administrative responses and performs no network calls: `python3 -B sso-service/test_phone_configuration.py`. It checks the read-only default, repeatable updates, unrelated-field preservation, conflicting-mapper rejection, canonical phone patterns and equality of the readable/imported profile. It does not replace the pinned-provider browser smoke.
