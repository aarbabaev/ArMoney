# ArMoney identity provider

Runtime: `quay.io/keycloak/keycloak:26.7.4`, pinned from the [official downloads](https://www.keycloak.org/downloads.html). This directory is configuration, not a Java module. Mount `armoney-realm.json` read-only in `/opt/keycloak/data/import/` and start with `start --import-realm`. Keycloak supports [environment placeholders](https://www.keycloak.org/server/importExport); supply `SSO_CLIENT_SECRET` to Keycloak and auth-service. No user accounts or secret values are committed.

Use a dedicated PostgreSQL database/volume. Set `KC_HTTP_RELATIVE_PATH=/sso`, `KC_HTTP_ENABLED=true`, `KC_HOSTNAME` to the exact external HTTPS origin and `KC_PROXY_HEADERS=xforwarded` behind the trusted TLS edge. Do not publish the Keycloak application or management ports directly. The edge must overwrite forwarding headers and restrict administration endpoints. Startup import skips an existing realm: later configuration changes and secret rotation require deliberate administrative updates, not deleting its volume.

The `armoney-ios` public client uses authorization code with mandatory S256 PKCE. Its only callback is `com.armoney.ios:/oauth/callback`; its only post-logout callback is `com.armoney.ios:/oauth/logout`. Password grants, implicit grants, service accounts, device authorization and CIBA are disabled. The native client uses the system authentication browser, validates state, and exchanges the access token through auth-service; it does not use an ID token as authentication evidence. The server validates identity through authenticated introspection. Local session credentials are kept in Keychain. The private `armoney-auth` client authenticates server-side introspection and has no user grant flows or service account.

POST `/v1/auth/sso` accepts only `{ "access_token": "<provider access token>" }` (8192 characters maximum, 12288-byte body). Auth checks the provider's active result, expiry, issuer, API audience, issuing iOS client and subject. Provider failures return 503; unacceptable tokens return 401; malformed input returns 400. It creates/reuses a local UUID keyed by the exact issuer and subject. Email is never a linking key; `/v1/auth/me` returns `email: null` for these principals. Legacy credential identities remain separate even if the same person uses both methods. The result is a new independent 30-minute opaque ArMoney session; only its digest is stored.

POST `/v1/auth/logout` revokes only the supplied ArMoney session. The native client also opens the provider's OIDC end-session endpoint with client_id and the configured post-logout redirect, then clears local credentials. The provider may require confirmation because this flow supplies no ID-token hint. Provider logout/revocation does not revoke an already issued ArMoney session; its expiry/local logout remains authoritative. The current native client does not request offline access or implement refresh. It starts a fresh browser SSO flow when its ArMoney session expires.

CI should create disposable users administratively and add a loopback redirect to `armoney-ios` in its isolated realm only. Drive a real browser authorization request with S256, state and nonce, submit the Keycloak form, exchange the returned code with its verifier, then call the public exchange and protected profile APIs. Assert wrong verifier/state, redirect mismatch, wrong audience/client/issuer, local logout, provider outage and separate-owner isolation. Never enable a password grant to replace this flow and never seed the persistent developer stack.

References: [OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [client and PKCE configuration](https://www.keycloak.org/docs/latest/server_admin/index.html), [hostname configuration](https://www.keycloak.org/server/hostname).
