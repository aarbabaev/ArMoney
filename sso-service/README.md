# ArMoney identity provider

Runtime: `quay.io/keycloak/keycloak:26.7.4`, pinned from the [official downloads](https://www.keycloak.org/downloads.html). This directory is configuration, not a Java module. Mount `armoney-realm.json` read-only in `/opt/keycloak/data/import/` and start with `start --import-realm`. Keycloak supports [environment placeholders](https://www.keycloak.org/server/importExport); supply `SSO_CLIENT_SECRET` to Keycloak and auth-service. No user accounts or secret values are committed.

Use a dedicated PostgreSQL database/volume. Set `KC_HTTP_RELATIVE_PATH=/sso`, `KC_HTTP_ENABLED=true`, `KC_HOSTNAME` to the exact external HTTPS base URL including `/sso` and `KC_PROXY_HEADERS=xforwarded` behind the trusted TLS edge. Do not publish the Keycloak application or management ports directly. The edge must overwrite forwarding headers and restrict administration endpoints. Startup import skips an existing realm: later configuration changes and secret rotation require deliberate administrative updates, not deleting its volume.

The separate `armoney-ios` and `armoney-android` public clients use authorization code with mandatory S256 PKCE. Each has exactly one callback and one post-logout URI:

| Client | Authorization callback | Post-logout callback |
| --- | --- | --- |
| `armoney-ios` | `com.armoney.ios:/oauth/callback` | `com.armoney.ios:/oauth/logout` |
| `armoney-android` | `com.armoney.android:/oauth/callback` | `com.armoney.android:/oauth/logout` |

Password grants, implicit grants, service accounts, device authorization and CIBA are disabled. The native client uses the system authentication browser, validates state, and exchanges the access token through auth-service; it does not use an ID token as authentication evidence. The server validates identity through authenticated introspection. Local session credentials are kept in Keychain on iOS and Keystore-encrypted app-private no-backup storage on Android. The private `armoney-auth` client authenticates server-side introspection and has no user grant flows or service account.

POST `/v1/auth/sso` accepts only `{ "access_token": "<provider access token>" }` (8192 characters maximum, 12288-byte body). Auth checks the provider's active result, expiry, issuer, API audience, issuing client from the exact `armoney-ios`/`armoney-android` allowlist and subject. If `azp` is present, it must match that issuing client; listing both clients does not permit cross-client mismatches. Provider failures return 503; unacceptable tokens return 401; malformed input returns 400. It creates/reuses a local UUID keyed by the exact issuer and subject. Email is never a linking key; `/v1/auth/me` returns `email: null` for these principals. Legacy credential identities remain separate even if the same person uses both methods. The result is a new independent 30-minute opaque ArMoney session; only its digest is stored.

POST `/v1/auth/logout` revokes only the supplied ArMoney session. The iOS client also opens the provider's OIDC end-session endpoint with client_id and the configured post-logout redirect, then clears local credentials. The provider may require confirmation because this flow supplies no ID-token hint. Android currently removes its local bank session and attempts bank-session revocation; its browser SSO cookie may remain active. Provider logout/revocation does not revoke an already issued ArMoney session; its expiry/local logout remains authoritative. The native clients do not request offline access or implement refresh. Each starts a fresh browser SSO flow when its ArMoney session expires.

The disposable CI smoke adds one exact loopback redirect to each native client in its isolated realm only and creates synthetic users administratively. Drive a real browser authorization request with S256, state and nonce, submit the Keycloak form, exchange the returned code with its verifier, then call the public exchange and protected profile APIs. The browser script checks wrong verifiers, code replay, client/redirect binding, ID-token rejection, shared issuer/subject identity across native clients, local logout and separate-owner isolation. Adapter unit tests cover wrong audience/client/issuer, cross-client `azp`, malformed claims and provider failure. Native clients validate callback state independently. Never enable a password grant to replace this flow and never seed the persistent developer stack.

References: [OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers), [client and PKCE configuration](https://www.keycloak.org/docs/latest/server_admin/index.html), [hostname configuration](https://www.keycloak.org/server/hostname).

Keycloak 26.7.4 requires the authenticated introspection client to appear in the token audience. Both native clients' access tokens therefore have both `armoney-api` and `armoney-auth` audiences. Auth-service still requires `armoney-api` and an issuing client from the exact native-client allowlist; no introspection audience-check compatibility bypass is enabled. Both audience mappers exclude ID tokens. See the [pinned provider implementation](https://github.com/keycloak/keycloak/blob/26.7.4/services/src/main/java/org/keycloak/protocol/oidc/AccessTokenIntrospectionProvider.java).


## Existing realm upgrade

Editing this export and restarting with `--import-realm` does **not** update an existing `armoney` realm. Its users, client secrets and issuer/subject mappings remain in the persistent database. Adding Android to an existing realm requires an explicitly authorized administrator to create the separate `armoney-android` client with the exact settings above and the two audience mappers from this export, then verify the persisted configuration. Preserve the existing iOS and confidential `armoney-auth` clients, users, issuer URL and database volume. Do not delete/re-import the realm or rotate unrelated secrets to add Android.

The source change and disposable browser tests do not establish that a developer's running realm has been upgraded. No live administration commands are executed by this change. Native-device callback dispatch and LAN certificate validation also require device evidence beyond the browser loopback tests.
