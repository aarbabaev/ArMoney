# ADR 0045: Durable code confirmation anchors and original-key lookup

Status: Accepted design amendment; implementation and activation pending. Refines [ADR 0043](0043-code-intent-confirmation.md) and the [confirmation draft](../../auth-service/CODE-INTENT-CONFIRMATION-DRAFT.md) for #28/#36; those published documents and V12 remain unchanged. Independent QA, security and provider design reviews agreed these choices on 2026-10-17 against Auth d32b8b4 and unchanged C1 sources. Reviewed design SHA-256: eaf765fd366d39ab33df99c42023219a1d3a90d12d6ed05fcdbbe4ed5ef25a59. This is not evidence of implementation, migration, testing, deployment or banking authority. Concrete default-off configuration and runtime prerequisites remain open.

## Frozen constraints and conservative interpretation

The frozen CODE-INTENT-CONFIRMATION-DRAFT “Exact transaction ownership and lock order” says to commit an opaque anchor before HTTP, binding actor, intent, full request, DB start and authority identity/epoch/revision. The coordinator selected a DURABLE per-invocation record, not an ephemeral returned capability alone. Original V12 stage admission stays immutable. The six-field confirmation wire request acquires NO UUID/anchor/budget fields. Amendment B keeps one PRIMARY physical session/global16 permit across admission, HTTP and all transactions. Separate denial commit and fresh exact replay remain mandatory. The choices below define the accepted design. SQL and source changes require implementation review and listed acceptance evidence.

## Intent-scoped identity: SEC-C2-ANCHOR-001

BEFORE any anchor selection/allocation, verify the authenticated stable logical actor equals the ORIGINAL stage actor: recompute armoney-intent-actor-v1 using the intent's ORIGINAL retention key ID and compare its actor_hash. Also match original code_key_id, code_digest and four-field binding HMAC. Configured actor B cannot allocate FIRST or REPLAY for actor A's intent, even after A's FIRST expires; deny before allocation. Rotated directional credentials mapped to the SAME logical actor A retain A's original FIRST/start. Missing original key is503, never a new identity.

V13 immutable anchors: internal random UUID; intent UUID; original retention key ID; actor HMAC; six-field binding HMAC; deterministic business-confirmation HMAC; purpose FIRST/REPLAY; bounded generation; original DB start; canonical authority stamp HMAC; explicit epoch/revision; original code expiry; erase_at. No raw subject/client/session/auth-session/contact, request JSON, token or code. No authority/enrollment/identity FK. Intent FK only with child-before-parent retention, no live cascade.

Add partial UNIQUE(intent_id) WHERE purpose=FIRST. FIRST is intent-scoped, NOT merely actor/business-key-scoped. It is always generation0. Add UNIQUE(intent_id,purpose,generation), and result UNIQUE(intent_id), UNIQUE(proof_id), UNIQUE(business_confirmation_hmac). Derive latest generation under shared controls rather than introduce a mutable freshness cursor. Only the original stage actor can reach this derivation.

V13 immutable result: business-confirmation HMAC; original retention key ID; actor/binding/payload HMACs; intent UUID; original proof UUID; budget_origin_id CHECK(equal to intent_id); original expiry; retained_until=original code expiry+7 days. No duplicate recipient or raw binding. Avoid proof/reservation FKs that pin their existing shorter cleanup; validate their exact associations atomically when creating the result. Result does not mint authority.

Business confirmation identity keeps frozen armoney-code-confirmation-v1 over length-prefixed logical actor, immutable intent UUID and canonical full CodeBinding in order: code_digest, code_key_id, issuer, subject, client_id, user_session_id. Its material is the ORIGINAL intent retention key, not current credential/key selection. New domains for the pending implementation: armoney-confirmation-binding-v1 over those six fields; armoney-confirmation-anchor-actor-v1 over logical actor; armoney-confirmation-authority-v1 over the twelve-field stamp below.

## Exact canonical authority stamp

Actual PostgresCodeIntentStore.stamp has TWELVE fields after armoney-intent-authority-v1. Preserve its existing domain/bytes and stored hash unchanged. The new confirmation authority domain uses EXACTLY this same ordered field sequence:

1. marker identity UUID
2. authority enrollment UUID
3. authority state literal
4. verification_epoch
5. authority revision
6. email_candidate_id
7. phone_candidate_id
8. projection_operation_id
9. projection_revision
10. projection_command_id
11. authority expires_at
12. enrollment expires_at

Use canonical lowercase UUID, decimal integers without sign/leading zeroes, original DB Instant.toString timestamp precision, nullable UUID as empty string, four-byte-length-prefixed UTF-8, and original retention key. Explicit epoch/revision must equal the hashed values. Check pending=mapped=marker identity and exact issuer/subject association directly while locked; six-field request binding HMAC separately covers the subject/session tuple. Receipt/candidate versions, grant and full six-field ACK/recovery/deadlines are independently revalidated: this stamp never replaces those checks. A changed original stage authority hash cannot be repaired by silently adopting a new stamp.

## Unresolved FIRST versus COMMITTED replay

FIRST_UNRESOLVED = durable FIRST exists, result absent. Every concurrent/request retry maps the unchanged six fields to the SAME intent-scoped FIRST UUID/start after original actor validation. No resampling, new generation, new fresh window or expiry extension. FIRST_SPENT = original observation window/code/authority bound no longer usable, or stamp changed. Keep the row and deny; fresh authorization is required, never another FIRST for this intent.

COMMITTED = immutable result exists. A legitimate exact replay needs fresh CURRENT provider evidence but retains original proof/event/bytes/expiry and zero new hourly debit. Only the transaction that INSERTS a new REPLAY anchor receives the one-shot provider-call capability for that generation. Competing callers cannot share it, perform another call, or allocate another generation:503/fresh authorization. A new generation is allowed only AFTER the preceding original observation window is spent AND authoritative durable completion proves that preceding external call ended. No completion proof means503/fresh authorization even if time elapsed. Mere elapsed time, PID disappearance, process health, connection timeout or presumed lease expiry is NOT definitive completion.

Use a third bounded technical table `sso_code_confirmation_anchor_completions`: immutable anchor UUID primary key/FK, original proof UUID, original DB completed_at. It is written only in a successful current POSITIVE replay final transaction AFTER the one provider response has fully completed and all final checks pass. It carries no fresh authorization, start/expiry replacement, event or recipient. At most one row per anchor, global100000 cap inherited from anchors, same erase_at/child-before-anchor retention. The FIRST result itself proves its provider response completed, so no separate FIRST completion row is needed. Failed/stale/negative/uncertain operations allocate NO completion marker; in particular negative denial still writes authority only. A lost acknowledgement of a replay-completion COMMIT must be reconciled by authoritative state under controls; do not assume completion without that row. This explicit outcome record, rather than an inferred timeout, permits later bounded replay generations. No new HTTP field is introduced.

NO concurrent duplicate external calls for an anchor. Under shared controls, the acknowledged INSERT creator alone obtains an opaque, thread/request/backend-bound capability with a one-shot call flag. A pre-existing unresolved FIRST is busy/spent and ALWAYS503/fresh authorization to another request; neither definitive prior failure nor elapsed time permits a replacement FIRST. Rotated credentials do not change this. This availability choice avoids a new ownership lease, takeover heuristic or additional claim namespace. Each capability performs at most one call and cannot be reused even after an exception. A reconnect or unknown COMMIT returns no capability. The authoritative positive result/completion markers above permit only the separately bounded already-COMMITTED replay policy, never a new FIRST. No polling, inline retry or reanchoring.

## One aggregate four-second lookup+confirm budget

The PROVIDER captures ONE System.nanoTime-style monotonic start BEFORE key lookup, including before DNS, connect, Auth admission/body work and local serialization. Lookup + body completion/parsing + local selection + ONE confirmation + full confirmation response/body/claim handling share FOUR seconds TOTAL. If original key is already immutable/known, start before confirmation. Before every phase compute only remaining time from that original start. No reset at lookup success, no previous-key confirmation loop, no polling/inline retry. Exhausted budget means NO confirm is sent; if confirm was already sent, outcome may be uncertain and token is withheld. A client timeout omitting DNS or body is insufficient. The provider owner must prove cancellation/bounding of those phases on the pinned implementation; source alone is not that proof.

No browser timeout/header or new DTO field is accepted by Auth. Auth's own inbound-body deadline and DB observation anchor are additional independent bounds, not proof of this producer aggregate budget. Required cases: slow/stalled/drip lookup, slow admission, delayed body, time consumed between calls, slow confirm, cancellation and exhaustion before confirmation; no new call after exhaustion. Original OAuth single-use code is consumed before the response hook: no resurrection or retry of that code after uncertainty; fresh authorization is required.

## Exact shared lock order, reconciled to source

Required combined order:

V control -> projection control -> proof control -> encryption catalog rows sorted by key_id (and nonce/fence children when required) -> authority/enrollment class -> identity/permanent-marker/external-mapping class -> candidate/receipt/challenge class (stable purpose/UUID) -> projection command/tombstone/completion-intent class -> code-intent parent -> stage alias/detail and confirmation anchor/result idempotency class -> V7 event -> proof -> proof-command.

Actual stage calls catalog.synchronize BEFORE authority/enrollment SELECT, then identity/marker/mapping and intent. Cleanup calls catalog.synchronize BEFORE intent victims. Therefore authority-before-catalog was incorrect. Preserve these source-compatible edges. Stage currently locks authority/enrollment together with FOR UPDATE OF a,e, not a separately guaranteed enrollment-before-authority ordering; they form one serialized class under exclusive shared controls. Paths omitting catalog skip it, but any later C writer needing catalog must acquire it before authority. No callback already holding authority may newly acquire catalog.

Under controls, an immutable nonlocking intent metadata read may locate association/enrollment; it is not allocation/authority permission. Then lock catalog and ordered authority/business rows, lock intent, reread exact binding/actor and reconstruct original13 fields via original first alias and AEAD/AAD. Current reconstructInTransaction locks catalog then intent: extract a caller-owned core usable AFTER earlier authority locks, rather than call it first and acquire authority afterward. Cleanup uses catalog->intent->children subsequence and never reacquires earlier authority. Final checks reread already-owned rows; no new earlier locks, nested transactions, hidden pool borrow or HTTP under locks.

## Owned-session phases and immutable time

Credential authentication -> existing HTTP/1.1 absolute body deadline -> one global permit/PRIMARY session -> committed shared20/refill2 admission exactly once -> strict six-field parse. Preflight locks as above, reconstructs original Write/hash, validates original actor, original stage admission and current stamp, selects the original intent state and INSERTS a new permissible intent-scoped anchor/start only for its sole owner, rechecks original bounds, COMMITs. Existing unresolved anchors return503, not a call capability. Return a live one-shot request-bound capability ONLY to the acknowledged INSERT creator after COMMIT and permit verification.

Get ONE exact v2 observation outside transactions on this same owned connection/slot. It binds issuer,subject,client,user_session, canonical nullable contacts, enabled,user_session_active,client_session_active and observed_at/valid_until. Old8/11-field/pretoken Flow DTOs are invalid. Capture DB receive without renewing original start: receive>=start, receive-start<=4s. Require integer delta=valid_until-observed_at in1..5 and effective_deadline=min(start+5s,start+(delta-1)s); delta1/equality/empty/backward/uncertain denies. Never resample start after admission/locks. Equivalent clock-rate/continuity assumption remains runtime NO-GO.

Final transaction on same physical backend takes same ordered locks and rechecks original anchor/stamp, managed marker/mapping, both independent current receipt/candidate/version pairs, immutable grant/epoch, all six ACK fields/recovery, code/enrollment/authority/receipt/grant/projection and effective deadlines. Positive atomically writes V7 event/proof/proof-command + V13 result. Recheck AFTER all inserts and before commit; failure rolls back all positive effects. Consume original V12 timely stage admission: do not reopen issued+30s CREATE at confirmation and do not reserve creation again.

Fresh exact negative at SAME stamp uses existing monotonic invalidation. No old negative applied to a changed stamp/identity. Already suspended does not advance epoch. Recheck freshness AFTER suspension update; stale attempt rolls back that attempted transaction. Commit DENIED_COMMITTED internally, THEN generic409 outside transaction. No proof/event/result/alias/audit. Missing/malformed/503/uncertain evidence is UNAVAILABLE, not revocation. Positive caps/cleanup health cannot block an already admitted fresh negative.

## Unknown COMMIT: strict predecessor completion

Unknown anchor COMMIT returns NO capability and makes NO provider call. Dispose uncertain physical connection using existing protocol. Reconciliation is allowed ONLY when definitive predecessor completion can actually be established under the original controls and authoritative state; otherwise503/fresh authorization. Acquiring controls is necessary, not an invented transaction-completion heuristic. PID/connection disappearance, elapsed timeout, a failed HTTP exchange or an absence read alone cannot establish the required completion. A visible FIRST always retains its UUID/start and NEVER issues another request's provider capability. A committed positive result/completion marker is authoritative evidence of the completed provider response; a generic failure record is not.

Do not implement an absent-row recovery branch that silently assumes the predecessor rolled back. If no definitive original completion evidence exists, preserve uncertainty and require a fresh authorization code. The unchanged six-field request cannot identify a cross-node ephemeral predecessor or carry an internal invocation UUID. The safe producer rule is no retry of that consumed code after uncertainty; ordinary FIRST admission for a genuinely new code remains distinct. Stronger cross-node proof of absent predecessor completion would need a separately approved durable protocol, not a heuristic or DTO expansion. No such recovery shortcut is permitted by this design.

Unknown result COMMIT withholds response/token and preserves identity. Legitimate request finds COMMITTED -> current REPLAY facts/original snapshot; unresolved -> ORIGINAL FIRST/start. No new event/result identity or code resurrection. Historical resolve never substitutes for confirmation. The unchanged six fields map internally; no invocation UUID goes onto wire.

## Correct authoritative hourly accounting

Actual PostgresLoginCreationBudget.requireAvailable counts recent reservations PLUS recent proofs lacking a reservation with the SAME proof UUID. V12 reservation ID is intent UUID; new V7 proof has DIFFERENT UUID. Merely skipping a second reserve(PROOF) still double-counts the confirmed proof as legacy-unreserved. C2 must change that counter using authoritative immutable confirmation-result mapping.

At result creation, validate under shared controls the existing original INTENT reservation and exact intent; bind UNIQUE proof_id to intent_id/budget_origin_id, with budget_origin_id=intent_id. Validate proof/reconstructed Write/result association atomically. Do not create or retime a reservation. No reservation FK that pins a65-minute budget row through7-day result retention. Store enough immutable origin association to survive reservation pruning without extending its window.

Count = reservations whose ORIGINAL created_at is inside trailing hour + recent proofs with neither same-ID reservation NOR a valid immutable V13 confirmation mapping to their ORIGINAL INTENT budget origin. Exclusion must follow that exact committed intent/proof/result association, not arbitrary incoming proof IDs. Ordinary reserved PROOF rows still count once. Pre-V12 and other legacy unreserved proofs have NO V13 origin mapping and keep counting normally. Once the original INTENT reservation ages outside the hour or is pruned, do not recreate its charge or start counting its mapped proof as newly created. Unique proof/intent mappings and immutable association prevent excluding unrelated proofs. Controls serialize writers; proof and mapping commit in SAME transaction, so no intermediate unassociated proof is externally visible.

Mandatory exact acceptance:999 counted legacy creations + one timely stage INTENT =1000. Confirm/replay/lost ACK remains1000, zero new reservation rows, original reservation timestamps unchanged. New unrelated stage/legacy creation is429. Cover pre-V12 unreserved proofs, ordinary reserved proofs, mapping forgery/uniqueness, rollback, rotation, original-hour rollover and reservation cleanup. No test weakening or free orphan-stage credit.

## Accepted capacities, retention and denial exemption

Independent anchor cap100000 globally, max32 rows/intent (one FIRST+31 REPLAY). Keep FIRST and every allocated generation until ORIGINAL code expiry+5minutes, even if their evidence window is spent: premature deletion could resurrect FIRST/generation. Replay completion markers are capped one-per-anchor/100000 globally, erased with their anchor at original expiry+5minutes. Result tombstones and original intent last original expiry+7days. No recycling/start mutation. Hard anchor capacity means503 before a new provider call; no reuse/takeover of another invocation's live anchor; do not claim status was checked. This is independent bounded authenticated-execution unavailability and has independent security design approval; implementation verification remains required, and it is not a disguised positive-create cap.

Positive tables retain existing100000 caps; exact current replay compares result before positive-create capacity rejection. Shared1000/hour accounting is the corrected original-intent accounting above. Full positive tables/unhealthy cleanup may NOT prevent new bounded anchor admission/provider-negative discovery when anchor capacity is available, nor application of a fresh already admitted negative; denial allocates no additional anchor/result/alias. Do not add unbounded reserved-denial storage or fabricated evidence.

Cleanup every30s, <=10 transactions/wake, <=100 rows/table/transaction,1s lock timeout; exact shared control/catalog/business order, parent lock before children, expired completion markers before their anchors, then results before parent deletion. Never purge unexpired rows for space. Extend health to anchor/result overdue>5minutes and ANY table>=80% alert (not hard80% admission). Health gates new POSITIVE result creation, not fresh negative discovery/application or valid existing-result replay. Retain original HMAC keys through actual final anchor/tombstone purge; AEAD keys through actual final detail purge. No new PII foreign keys or erasure SLA during outage.

## Exact read-only key selection amendment

Private POST /internal/sso-code-intents/key, never public ingress. Dedicated printable ASCII32..256 credential `SSO_CODE_INTENT_LOOKUP_KEY` in exactly one `X-ArMoney-Code-Intent-Lookup-Key` header. That environment name is the normative shared spelling for the pending implementation. Missing/duplicate/wrong header401 before gate/admission/body parsing; caller actor headers ignored. Server configuration maps it to the stable original stage logical actor and exact permitted issuer/client PAIRS. Stage write, resolve, confirmation, lookup, status, bridge and any other configured secret/code/retention/encryption material must be independently provisioned: startup rejects equality of raw or decoded bytes, missing required material/actor/scope, invalid flags or ambiguous pair scope. No credential provision/flag enablement follows from this draft.

Exact JSON request object has FIVE fields, no additional/null/duplicate keys: issuer,subject,client_id,user_session_id (nonblank whitespace/control/surrogate-free strings, maximum lengths512/255/128/255 respectively; exact allowlisted HTTPS issuer/client pair, no trimming/coercion), candidates (array length1..2). Each candidate is EXACTLY {code_key_id,code_digest}; ID must match [A-Za-z0-9_-]{1,32} and the configured allowlist; digest is exactly64 lowercase hex. Candidate key IDs AND digests each unique: duplicates/malformed/wrong-type/unknown fields400. Do not accept actor, anchor UUID, raw code, root/tab/session notes, timestamps or browser-selected principal. HTTP1.1 and existing absolute inbound body deadline apply after directional auth; global16/shared20-refill2 admission precedes parsing. JSON request/response max12KiB, no redirects/logged bodies/digests, fixed private destination.

Use existing V12 UNIQUE(code_digest), <=2 point reads; NO new lookup index/migration. Each row must match candidate code_key_id, unexpired ORIGINAL code bound, original actor HMAC and four-field binding HMAC under row's ORIGINAL retention key. V12 binding is armoney-intent-binding-v1 over issuer,subject,client,user_session; actor separately armoney-intent-actor-v1. Payload HMAC is NOT reconstructible from lookup tuple and cannot serve this index. Check original expiry again before response. No authority grant or current proof/result lookup is performed.

Exactly one matching intent ->200 application/json with EXACTLY {code_key_id: original ID}; no intent/proof/event/authority metadata. Zero matching intents ->generic404; more than one matching intent ->503 (including inconsistent candidates resolving distinct matches). Missing original retention key503, never silently treating unreadable candidate as absent; malformed/duplicate candidates400; scope/binding mismatch generic denial409; capacity/rate429; unavailable/uncertain/backend503. Authenticated outcomes use Cache-Control:no-store, application/json, EXACT generic error JSON {"error":"code_intent_request_rejected"} without binding/digest/keys/secrets. All failures stay failures; no historical fallback. No business writes; only bounded shared abuse admission state/technical gate may change.

Then ONE unchanged six-field confirm under SAME original producer deadline. Current/previous code-digest keys must remain on ALL provider nodes through the oldest original code expiry; no second rotation evicts a still-needed oldest key. Immutable intent row code_key_id is authoritative original selection; returned ID must match one offered candidate and retained local material. Unknown/unoffered ID fails, no guessing or another lookup loop. No inline confirm retry/previous-key404 confirmation loop.

## Producer deadline API and cancellation ownership

One invocation-owned monotonic Deadline begins BEFORE lookup serialization or DNS (or before confirm serialization if original key is already known). Its API supplies remaining duration and a fail-if-expired operation; BOTH sends, body subscribers/parsers, local selection and claim writes use that SAME object, never create per-call deadlines. Effective request deadline is the remaining aggregate4s, with2s connect bound further limited by remaining time. Check before starting confirm and immediately before claims/token release. After expiration, cancel the actual pending HTTP future/body subscription through their invocation owner and withhold token response. No per-request reader/DNS executor or abandoned task is created as a workaround. No shared client's unrelated calls are cancelled.

Current provider DeadlineHttp starts a new deadline per call and therefore does NOT implement this contract. Future implementation must share one explicit deadline/cancellation owner across lookup and confirm. Cancelling an HTTP future DOES NOT prove platform DNS resolution was cancelled/bounded. Pinned JDK21 slow-resolution actual evidence remains a runtime-GO blocker; source-only Java timeout configuration, connect/read mocks or a completed cancellation future cannot close it. If DNS cannot be bounded by the approved platform seam, runtime stays NO-GO rather than claiming four-second total or adding an abandoned executor. Distinguish bounded token-authorizing wait from physical orphan work; global16 admission does not prove global physical HTTP/DNS worker cancellation.

## Classification and activation limits

Explicit server-configured managed issuer/client PAIRS cover ALL subjects in each pair and are disjoint from separately explicit legacy PAIRS. Compare exact validated configured pair membership, never independent issuer-set/client-set Cartesian products or silent request normalization. Startup rejects overlap/duplicate/ambiguous pairs; an unknown pair denies rather than selecting legacy. Both producer and Auth adapters validate the same managed pair scope; token/browser claims cannot select a different path. Auth permanent marker remains authoritative. Mixed legacy/managed same-pair routing is UNSOLVED and activation NO-GO, not solved through missing-marker fallback/mutable notes/new classification endpoint. Direct six-field successful confirmation is sole CURRENT claim source; historical resolve cannot authorize. Refresh strips all three claims from BOTH access/refresh with no remote writes; introspection preserves original validated claims only. No banking session/profile/notice is created; managed banking denial remains.

## Concrete Auth design choices

- Exact HMAC strings and twelve-field source-compatible authority stamp are fixed above; no alternative domains, current-key fallback, field reordering or mutable stamp repair.
- FIRST uniqueness is partial UNIQUE(intent_id), original actor equality precedes any allocation; sole acknowledged creator owns its one external call. Busy/unresolved losers503/fresh flow, no takeover/reanchor.
-32 anchors/intent (FIRST+31 REPLAY),100000 anchors and at most100000 one-per-anchor completion markers, original code expiry+5minute anchor/completion retention. Bounded capacity unavailability is accepted, never permission to bypass freshness or authorize. No generation is recycled.
- New REPLAY only after prior window spent AND its immutable positive completion row exists; otherwise503/fresh flow. FIRST positive result is its completion evidence. No negative-side completion/audit row and no epoch storm.
- Core extraction is concrete: add caller-owned lock-aware reconstruction and proof-write functions receiving the existing DSL/owned request; acquire catalog before authority/intent, skip only confirmation's second fresh-CREATE window/hourly reservation, retain all existing final current evidence/deadline checks; no nested store request or pool borrow.
- Counter mapping policy is concrete: immutable unique result(proof_id,intent_id,budget_origin_id=intent_id), validated original INTENT reservation at creation, no reservation FK/retiming, exact mapped-proof exclusion from legacy-unreserved counting through reservation pruning; all ordinary pre-V12/unreserved/reserved proofs unchanged. Test999+stage=1000 throughout.
- Uncertain absent-predecessor completion has NO recovery heuristic:503/fresh authorization when authoritative completion is unavailable. Reconciliation cannot mint a capability for an existing FIRST or resurrect OAuth code.

The provider design agreement requires that the producer accept503 busy/uncertain => fresh authorization with NO inline retry; own one true aggregate4s lookup+confirm budget including DNS/body/admission and abort before exhausted confirm; bind original key selection and explicit managed/legacy PAIRS. Auth cannot infer that producer budget or cross-node predecessor from six fields. Any provider request for takeover/retry/stronger absence recovery requires a separate joint amendment. Mixed-pair routing, equivalent-rate clock assumptions and pinned-JDK21 aggregate DNS/deadline/cancellation evidence remain activation NO-GO. This accepted design requires concrete default-off configuration and source/schema implementation review; it is not runtime or activation approval.

## Current source boundary
